# Decisions 기반 발화 완료 판단 및 상시 마이크 수정 계획

- 작성일: 2026-10-09
- 상태: 구현 및 자동 검증 완료. 실제 마이크 품질 평가 미실행. [구현·검증 기록](evidence/2026-10-09-decisions-speech.md) 참조.
- 확정 요구: 사용자가 마이크를 상시 켜놓을 수 있어야 한다. 띄엄띄엄 이어지는 발화를 모아 Decisions API로 완료 여부를 판단하고 보정한다. 마지막 발화 이후 대기는 최대 10초다. 빈 `듣고 있어요…` 행이 반복되지 않아야 한다.

## 1. 현재 확인한 동작과 문제

| 위치 | 확인한 내용 | 수정 방향 |
| --- | --- | --- |
| `packages/audio-client/src/dsp.ts` | 음량 기반 VAD가 700ms 침묵 또는 20초 구간 길이에서 commit한다. 침묵 자체로 마이크를 끄지는 않는다. | 전송용 음성 구간과 의미 단위의 문장 묶음을 분리한다. |
| `packages/ai/src/speech.ts` | commit마다 `finishSegment()`가 독립적으로 보정 전사를 요청한다. | 여러 구간을 묶어 한 번의 보정 요청으로 처리한다. |
| `packages/audio-client/src/controller.ts`, `transport.ts` | `audio.error`가 전체 캡처 실패와 마이크 해제로 이어진다. | 발화 처리 오류와 연결·장치 오류를 구분한다. |
| `apps/web/src/shared/audio.tsx` | 캡처 error 상태에서 사용자의 enabled 설정을 해제한다. | 사용자의 켜짐 의도와 실제 연결 상태를 분리한다. |
| `apps/web/src/features/study/StudyPage.tsx` | 빈 원문을 모두 `듣고 있어요…`로 표시하고 최근 3행에 포함한다. | 텍스트가 있는 발화만 목록에 표시하고 대기 안내는 한 곳에 표시한다. |
| `packages/ai/src/jobs.ts` | 미완료 전사가 하나라도 있으면 주제 종료가 실패한다. | 정상 무발화 완료와 실제 처리 실패를 구분한다. |
| `packages/ai/src/sentences.ts` | 구간별 원문·보정문 위치와 전체 텍스트 커버리지를 검증한다. | 묶음 단위 보정에 맞게 출처 계약과 검증을 함께 변경한다. |

실제 저장 기록에서 원문이 빈 보정 실패, 전사 실패, 주제 종료 실패를 확인했다. 다만 최초 음성 오류의 원본 예외가 보존되지 않아 정확한 원인은 확정되지 않았다. 침묵 타이머가 직접 마이크를 끈다고 단정하지 않는다.

## 2. 목표 동작

1. 사용자가 마이크를 켜면 침묵 중에도 켜짐 설정을 유지한다.
2. 원문 전사는 도착하는 대로 화면에 표시한다.
3. 짧은 침묵으로 나뉜 구간을 같은 화자·같은 주제의 열린 묶음에 누적한다.
4. Decisions가 현재까지의 발화를 완료로 판단하면 묶음을 확정하고 누적 PCM으로 보정 전사를 한 번 요청한다.
5. 미완성 또는 불확실하면 기다린다. 새 발화가 들어오면 대기 기준을 갱신한다.
6. 마지막 발화 이후 10초가 되면 판정 결과를 더 기다리지 않고 묶음을 확정한다.
7. 주제 종료 또는 사용자의 마이크 끄기에서는 남은 발화를 즉시 확정하고 처리한다.

예: `I participated…` → 대기 → `…in a hackathon…` → 추가 판단 → `…last weekend.` → 전체 음성 보정.

보정은 기존의 음성 기반 인식 보정을 유지한다. Decisions는 보정 시점만 판단하며, 인식 보정 단계에서 문법 교정·번역·미완성 문장 창작을 하지 않는다.

## 3. 대기 시간과 판정 정책

| 항목 | 계획값 / 규칙 |
| --- | --- |
| 초기 판정 | 마지막 발화 이후 약 1초 침묵, 해당 구간의 최종 원문이 준비되었을 때 |
| 최대 대기 | 마지막 발화 이후 10,000ms |
| 새 발화 | 발화 시작 즉시 기존 판정을 무효화하고, 새 발화가 끝난 시점부터 10초를 다시 계산 |
| 판정 종류 | `complete`, `continue`, `uncertain` |
| 즉시 확정 | `complete`이고 초기 신뢰도 기준 0.85 이상. 이 값은 실발화 평가 후 조정 |
| 미완성·불확실·낮은 신뢰도 | 추가 발화 또는 10초 마감까지 대기 |
| 반복 호출 | 같은 원문 revision으로 재호출하지 않는다. 내용이 추가된 뒤 침묵할 때 다시 판단 |
| Decisions 제한시간 | 초기값 2초와 남은 대기 시간 중 짧은 값. 실패·지연 시 10초 기준으로 처리 |
| 묶음 크기 상한 | 초기값 누적 PCM 60초. 전송용 구간 경계에서 분할하고 이어지는 발화는 다음 묶음으로 처리 |

10초는 **보정 결과를 받기까지의 SLA가 아니라 문장 묶음을 열어두는 최대 침묵 시간**이다. API 응답 시간은 별도다. 원문 전사가 10초보다 늦어도 묶음 경계는 10초에 고정하며, 원문 대기를 유한하게 제한한 뒤 실패·재시도로 처리한다. Decisions 지연 때문에 경계를 늦추지 않는다.

시간은 서버의 단조 증가 시계를 기준으로 관리한다. 브라우저는 샘플 기준 마지막 유효 발화 위치와 발화 재개를 전달한다. 현재의 `startedAt + 전체 PCM 길이`에는 trailing silence가 포함되므로 이를 그대로 마지막 발화 시각으로 사용하지 않는다. VAD의 700ms 대기 시간을 10초에 중복 가산하지 않는다. 클라이언트가 보낸 시각·offset은 범위를 검증하며 네트워크 지연 허용 오차를 별도로 측정한다.

`complete`는 문법적 완벽함이 아닌 대화상 마무리 여부다. 짧은 대답, 문법 오류, 한국어·영어 혼용도 완료일 수 있다. 다음 말을 완벽하게 예측할 수는 없으므로 완료로 확정된 뒤 이어지는 발화는 다음 묶음으로 처리한다.

## 4. Decisions API 연동

- 서버 전용 `POST /v1/decisions`, 모델 `gpt-6-luna`를 사용한다.
- 현재 프로젝트 키로 HTTP 200 및 choice 응답을 확인했다. 테스트는 언어 분류였으며, 문장 완료 판정의 품질·속도는 아직 검증하지 않았다. 해당 단일 호출은 약 3초가 걸려 제한시간 조정 평가가 필요하다.
- 입력: 누적 최종 원문, 짧은 직전 대화 맥락, 주제, 침묵 경과시간. 음성은 Decisions에 보내지 않는다.
- 출력: 완료 여부 choice와 confidence. 누락·거절·잘못된 형식은 `uncertain`으로 처리한다.
- 프롬프트는 뒤에 올 말이 필요한 접속사·전치사·미완성 구문을 고려하되, 문법 오류를 미완성의 유일한 근거로 삼지 않도록 한다.
- 발화 속 명령은 분류 대상 데이터로 취급한다. Decisions에는 앱 상태를 바꾸는 도구를 제공하지 않는다.
- provider 인터페이스에 완료 판단 메서드와 명시적인 반환 타입을 추가한다. 기존 SDK 지원 여부를 확인하고, 지원하지 않으면 서버의 작은 HTTP 어댑터로 연동한다.
- 모델명, 판정 제한시간, 신뢰도 기준을 서버 설정으로 관리한다. 사용자 확정 요구인 10초 상한은 별도 상수로 보장한다.

공식 자료: [Decisions 가이드](https://developers.openai.com/api/docs/guides/decisions), [Create a decision](https://developers.openai.com/api/reference/resources/decisions/methods/create).

## 5. 데이터와 처리 구조

### 5.1 전송 구간과 보정 묶음 분리

기존 `TranscriptSegment`는 원본 음성 구간과 실시간 원문을 보존하는 단위로 남긴다. 새 `SpeechGroup`을 문장 완료 판단·보정의 단위로 추가한다. 한 묶음이 반드시 문법적 한 문장이라는 제약은 두지 않는다.

묶음에 필요한 정보:

- ID, study/topic/speaker ID, 정렬 기준, revision.
- 순서가 있는 segment ID 목록과 원문 revision 목록.
- `collecting / deciding / correcting / ready / no_speech / failed` 상태.
- 누적 원문, 묶음 보정문, 최초·최종 발화 시각.
- 확정 이유: Decisions 완료 / 10초 경과 / 마이크 끄기 / 주제 종료 / 크기 상한.
- 처리 시도 ID와 단계별 오류. 생성 시점부터 저장하고 결과는 revision 조건을 검사하는 트랜잭션으로 반영한다.

동일 화자·주제에는 열린 묶음을 하나만 허용한다. 다른 참여자의 음성과 원문을 합치지 않는다. 다른 화자가 중간에 말해도 자신의 열린 묶음은 독립적으로 유지하고, 화면 정렬과 출처는 개별 구간 시각으로 추적한다.

### 5.2 원문·보정문·재생 출처

묶음 전체 보정문을 첫 segment에 몰아넣거나, 보정문을 추측으로 조각내어 기존 segment의 필드에 넣지 않는다. 다음을 명시적으로 분리한다.

- 원문 출처: segment ID + 원문의 UTF-16 범위.
- 보정 출처: group ID + 보정문의 UTF-16 범위.
- 재생 출처: 순서 있는 segment 오디오 목록 또는 묶음 오디오와 구간 offset.

`Utterance`, source range 계약, 문장 분할·피드백·리뷰·학습 기록·재생 로직을 함께 갱신한다. 누적 원문을 만들 때 사용하는 구분자와 원문 위치 매핑은 결정적으로 구성한다. 원문과 보정문 전체를 누락·중복 없이 커버하는 검증을 유지한다. 기존 기록은 구형 source range를 읽는 호환 경로를 유지하고, 신규 기록은 버전이 있는 묶음 출처를 사용한다.

### 5.3 동시성 및 중복 방지

- 발화 시작, 마지막 발화 갱신, 원문 추가, 판정 반환, 마감, 종료를 스트림의 직렬 처리 경로에서 조정한다.
- 판정에는 group ID, revision, activity generation을 붙인다. 원문이 아직 안 바뀌었어도 새 발화가 시작됐다면 이전 판정을 버린다.
- 10초 타이머도 generation을 검사한다. 활성 발화 중에는 침묵 마감으로 자르지 않는다.
- 확정은 한 번만 성공하는 상태 전이로 구현한다. Decisions 반환·10초 마감·종료가 겹쳐도 보정 작업은 하나만 생성한다.
- 보정 요청이 시작된 묶음은 동결한다. 후속 발화는 새 묶음으로 보낸다.
- 종료 이후 늦게 도착한 결과와 이전 재시도 결과는 현재 상태·revision 검사로 반영을 차단한다.
- 순서가 뒤바뀐 원문 완료 이벤트는 segment 순서로 모은다. 앞 구간 원문이 미완료이면 뒤 구간만으로 완료 판정하지 않는다.

## 6. 상시 마이크와 오류 복구

- `micEnabled`는 사용자 선택, 캡처 상태는 실제 장치·연결 상태로 분리한다.
- 구간 또는 묶음 보정 실패는 비치명적 이벤트로 전달하고 계속 듣는다. 해당 묶음만 재시도할 수 있게 한다.
- 연결 오류는 재연결 상태로 표시한다. 초기 정책은 1초·2초·4초 간격의 최대 3회 시도이며, 실패 시 재시도 버튼을 제공한다. 꺼짐 버튼은 재연결 중에도 즉시 작동해야 한다.
- 재연결 시 이전 스트림 종료 확인, 구간 ID 기반 중복 방지, 미확인 PCM의 제한된 보관·재전송을 함께 설계한다. 단순히 새 연결을 여는 것으로 복구 완료로 간주하지 않는다.
- 권한 거부·장치 제거는 명시적 조치가 필요한 오류로 안내한다. 사용자 켜짐 의도를 실제 녹음 중 표시와 혼동하지 않는다.
- 주제 종료·리뷰 동안 음성 전송은 중단하되 켜짐 설정을 유지하고, 다음 talking 주제에서 자동 재개한다. 스터디 종료·사용자 끄기·화면 해제에서는 장치를 정리한다.
- 장시간 대기 중 provider 세션 만료도 고려한다. 현재 다음 segment 시작 때만 수행하는 세션 교체를 유휴 상태에서도 안전하게 실행하도록 보완한다.
- 완료된 PCM과 종료 스트림 참조를 정리해 상시 사용 중 메모리가 계속 늘지 않도록 한다. 재시도에 필요한 음성은 저장소에서 조회한다.

## 7. 무발화와 화면 표시

- 원문이 공백뿐인 정상 전사 결과는 `no_speech`로 완료한다. Decisions·보정·피드백 요청을 생략하고 주제 종료를 막지 않는다.
- 전사 요청 실패는 `no_speech`로 치환하지 않는다. 빈 결과와 실제 오류를 구분한다.
- VAD에 최소 발화 지속시간과 시작·유지 임계값 분리를 추가하되, `yes`, `no` 같은 짧은 답변 및 작은 목소리의 첫 음절 보존을 검증한다. 수치는 녹음 fixture로 조정한다.
- 대화 목록은 의미 있는 원문 또는 보정문이 있는 항목을 먼저 고른 뒤 최근 표시 개수를 적용한다.
- 대기 안내는 마이크 영역에 하나만 표시한다. 묶음 원문은 계속 갱신하고 보정 요청 전에는 `이어서 말해 주세요`, 요청 이후에는 `인식 보정 중…`으로 구분한다.
- 숨겨진 실패도 놓치지 않도록 텍스트 없는 전사 실패는 별도 오류 안내와 재시도 상태로 노출한다.
- 대기·연결 상태 변화로 대화 목록 자동 스크롤이나 스크린리더 안내가 반복되지 않도록 한다.

타이머·경합은 fake clock과 지연 가능한 provider fake로 검증한다. 긴 대기를 실제 시간으로 반복하는 테스트는 피한다. API/DB 통합 테스트로 묶음 생성·확정·재시도·출처 저장의 원자성을 확인한다.

실행할 검사: `pnpm contracts:check`, `pnpm typecheck`, `pnpm test:unit`, `pnpm test:integration`, 관련 `pnpm test:e2e`, `pnpm build`. 필요한 서비스·환경이 없는 검사는 미실행 사유를 구분해 기록한다.

### 실제 음성 검증

- 1초·3초·9초 멈춤이 포함된 영어 발화, 한국어·영어 혼용, 짧은 답변, 말 고침, 끝이 열린 문장으로 평가한다.
- 작은 목소리·키보드 소리·무음 후 재개를 확인한다. 실마이크 5분 무발화 및 발화 재개를 수행한다.
- 조기 분리·불필요한 지연·보정 내용 누락, Decisions 지연과 fallback 비율을 기록한다. 데이터로 신뢰도 기준과 2초 요청 제한시간을 조정하되 10초 대기 상한은 유지한다.
- `I participate in marathon.`의 핵심 내용이 보정에서 누락된 기존 사례를 회귀 평가에 포함한다. 묶음 처리만으로 품질 문제가 모두 해결됐다고 간주하지 않는다.

## 10. 진단 로그와 범위

로그에는 단계, stream/segment/group ID, revision, 판정 결과·신뢰도, 확정 이유, 침묵 경과시간, 요청 소요시간, provider request ID, 오류 코드·정제한 메시지를 남긴다. API 키·원시 PCM·발화 전문은 기본 로그에서 제외한다.

구현에는 프런트 화면뿐 아니라 계약·저장·음성 처리·주제 종료·리뷰 출처 변경이 필요하다. 공개 API 응답 형식은 구현 시 공식 문서와 계약 테스트로 재확인한다. 현재 구현 결과와 검증 범위는 [구현·검증 기록](evidence/2026-10-09-decisions-speech.md)에 기록한다. 서버 재시작과 배포는 수행하지 않았다.
