# PRD 추적표와 MVP 인수 기준

상태: 인수 기준. 제품 코드와 로컬 실행 환경의 실제 검증 결과는 [로컬 검증 기록](evidence/local-validation.md)에 기록한다. 아래 표는 요구사항 추적표이며, 구현 또는 자동 검사 통과만으로 두 물리 기기·실마이크 인수를 완료 처리하지 않는다.

이번 대화에서 확인한 두 기본값도 검사한다: 첫 주제에 맥락/표현이 모두 없으면 경험 입력을 안내하고, 두 next 요청 문구가 동일한 승인·저장·생성 동작으로 연결된다.

A01~A27은 배포 전 G3에서 [로컬 실제 환경](local-validation.md)으로 통과해야 한다. A28은 G4의 AWS 항목이므로 로컬 기록에는 ‘AWS 배포 후 확인’으로 남긴다. G3 통과 후 AWS에 배포하고, G4에서 같은 기능 흐름과 배포 환경 차이를 확인한다. 배포 URL이 생긴 것만으로 로컬 미실행 항목을 통과 처리하지 않는다.

## 2. 자동 검증의 범위

| 계층 | 필요한 검증 | 실제 외부 호출 여부 |
| --- | --- | --- |
| 계약 | fixture/DTO/event validation, strict tool schema, typed client | 없음 |
| 도메인 통합 | 실제 PostgreSQL 트랜잭션·unique 제약·revision·소유자 scope | DB만 실제 |
| UI 흐름 | MSW와 event fake로 각 상태·동의·편집·오류 검사 | 없음 |
| 브라우저 통합 | 독립 A/B context의 초대·공통 상태·개인 분리 | 실제 API/DB, AI는 mock/live 표시 |
| AI smoke | 실제 OpenAI 전사·보정·도구·피드백·이미지 | 있음, 별도 명령으로 명시 |
| 로컬 실기기 G3 | 두 물리 노트북·신뢰된 로컬 HTTPS·마이크·재시작 후 저장 조회 | 실제 API/로컬 PostgreSQL/파일/OpenAI |
| AWS 실기기 | 두 물리 노트북·마이크·CloudFront WSS·저장 | 모두 실제 |

단순 스타일 수치마다 테스트를 추가하지 않는다. 상태 전이와 잘못된 데이터 귀속·중복 저장·공유 노출을 잡는 검증을 우선한다. mock 결과만으로 A25/A28을 통과시키지 않는다. 로컬 파일 저장 성공은 S3·IAM 확인을 대신하지 않는다.

## 3. 실제 두 기기 인수 시나리오

E01~E08은 먼저 G3의 로컬 HTTPS URL에서 수행한 뒤 G4의 AWS URL에서 수행한다. 환경별로 사용자·데이터·결과를 구분하며, 로컬 테스트 데이터를 AWS로 복사해야 할 필요는 없다. 아래 ‘서버’는 각 검증 단계의 실제 API다.

### E01. 가입·초대·맥락 없는 시작

준비: 서로 다른 노트북 A/B, 동일 검증 URL(로컬 G3 또는 AWS G4), 새 아이디 2개. 한 기기의 두 탭만으로 대체하지 않는다. 로컬에서는 한 호스트의 API·DB·파일 저장소를 공유한다.

1. A/B 가입. 동일 handle 재가입은 거절되는지 확인한다.
2. B가 개인 학습 화면에 있는 동안 A가 B의 아이디로 스터디 생성.
3. B에게 모달이 뜨고 참여하기로 입장. 양 기기의 studyId 확인.
4. 저장 경험이 없는 상태에서 시작하면 경험 입력 안내가 나오고 무관한 일반 주제가 생성되지 않는지 확인.

증거: 아이디 중복 결과, B의 타 화면 모달, 공통 ID, CONTEXT_REQUIRED 결과.

### E02. 경험 입력의 두 분기

1. A는 “부산에 다녀왔어요” 입력 → 보충 질문 → 답변하지 않고 정리 → 원문/정리본 확인·수정 → 저장.
2. B는 장소·사람·사건·행동을 포함한 구체적인 경험을 입력 → 정리·수정 저장.
3. 기존 카드 수정 후 새로고침. 수정된 값이 서버에서 조회되는지 확인.
4. AI가 원문에 없는 사건을 경험으로 덧붙이지 않았는지 원문과 비교.

증거: 질문 skip, 최종 저장 payload/조회, 원문 대비 정리 결과.

### E03. 실제 대화·원문·보정

1. A 또는 B가 시작 요청. 실제 생성된 상황 이미지와 대화 지시가 두 기기에 같게 표시되는지 확인.
2. 각자 마이크 권한을 허용하고 자연스럽게 교대로 발화한다. 사용자 지정 전제대로 각 마이크에는 본인 음성만 입력되는 테스트 환경을 마련한다.
3. 예시 발화로 “I was 줄 서 있었는데, the staff called my name.”, “I goed there yesterday.”, “해커톤”, “human” 등 혼용·의도적 틀린 영어·고유명사를 포함한다.
4. 대화 중 raw와 보정이 하단에서 업데이트되고 발화자와 순서가 양 기기에 일치하는지 확인.
5. raw가 이미 정확하면 보정이 같아도 정상이다. ASR 오류가 있는 발화는 실제 오디오와 비교해 보정이 맞는지 확인한다. 실제 틀린 영어를 보정 단계에서 올바른 문법으로 바꿨다면 실패다.

증거: 테스트 발화 원문, 각 단계 결과와 모델 설정, 라이브 화면/로그의 segmentId·speakerUserId와 review의 utteranceId 연결. 생성 이미지는 G3에서는 로컬 파일, G4에서는 S3에 저장된 실제 bytes임을 확인한다.

### E04. 마지막 발화·검토·상대 문장 수정

1. A가 문장을 끝내는 직후 B가 주제 종료 요청.
2. closing 동안 마지막 음성까지 flush되고 review에 마지막 단어가 포함되는지 확인.
3. raw·보정·피드백 summary 토글과 펼친 상세를 확인.
4. B가 A의 보정문을 편집해 저장. 양 기기에 수정된 문장과 stale 표시가 나타나야 한다.
5. 그 문장 재요청. 다른 문장은 유지되고 최신 correctionRevision의 피드백만 갱신되어야 한다.

별도 입력으로 한 음성 구간에 두 문장을 연속 발화하고, 처리 경계를 넘는 긴 문장도 포함한다. review는 문장별 편집 행으로 나뉘고 raw의 단어가 누락되거나 새로 만들어지지 않아야 한다. 라이브 구간과 review 문장의 ID가 다를 수 있으므로 sourceRanges로 연결을 확인한다.

추가 자동 검사: 첫 피드백 응답을 지연시킨 채 보정문을 다시 수정한다. 이전 revision의 응답이 새 문장의 피드백을 덮어쓰면 실패다.

### E05. 개인 챗봇·공유 yes/no

1. A가 단어 뜻 질문. 개인 답변과 A 학습 저장을 확인하고 B 화면·네트워크 payload에는 없는지 확인.
2. A가 한국어 표현의 영어 표현 질문. 개인 저장과 yes/no가 제시되는지 확인.
3. 첫 표현은 no, 두 번째는 미응답, 세 번째는 yes를 선택한다.
4. yes 표현만 두 기기의 공통 영역에 표시되는지 확인. 중복 yes는 공유 하나만 생성해야 한다.
5. 다음 주제의 생성 입력 snapshot에 yes 표현만 들어가는지 확인. 앞선 private 문구가 공동 prompt에 섞이지 않아야 한다.

증거: A/B의 별도 chat/learning 조회, 제안 결정, 공유 목록과 생성 입력 ID. 개인 대화 전체를 배포 보고서에 복사하지 않는다.

### E06. 다음 주제·지명·문장 분기

1. review에서 A가 “다음 주제로 넘어갈게”, 이후 다른 주제에서 B가 “다음 주제 만들어줘”를 실행한다. 둘 모두 승인·저장·생성까지 이어져야 한다.
2. 승인 피드백 학습 항목이 편집자 B가 아닌 해당 발화자 A의 기록에 저장되는지 확인.
3. 특정 참여자 이름을 지명해 next를 요청. 해당 참여자의 경험 ID만 주제 근거로 사용했는지 확인.
4. 별도 테스트 데이터로 표현과 연결되는 경험이 없게 한다. 이미지 대신 표현을 활용하는 문장과 대화 지시가 나오는지 확인.
5. 첫 주제/다음 이미지/문장 각각 conversationInstruction이 있는지 확인.

topic 생성은 경험과 표현을 근거로 한 결과여야 한다. 동일 이미지를 두 클라이언트가 독립 생성하는 구조라면 실패다.

### E07. 중복 요청·실패 상태

1. 같은 review 주제에서 A/B가 서로 다른 commandId로 next를 거의 동시에 요청한다.
2. 승인 1회, 다음 ordinal 1개, 활성 생성 job 1개, 저장 학습 항목 중복 없음 확인. UI disabled만 확인하지 않는다.
3. provider adapter의 명시적 실패 주입으로 이미지/피드백 실패를 확인한다. UI running → failed, 서버 실패 기록, 자동 재시도 없음이 보여야 한다.
4. 실패한 동일 Topic 생성에 사용자가 새 요청을 하면 같은 ordinal에서 새 job을 실행하고 과거 학습 저장을 반복하지 않는지 확인.

실패 주입 테스트와 실제 OpenAI 성공 테스트는 별도 증거로 남긴다. provider 키를 노출하거나 계정에 불필요한 실패 요청을 반복할 필요는 없다.

### E08. 마지막 승인·개인 기록 영속성

1. 마지막 주제에서도 종료 → 피드백 검토 → 최종 스터디 종료를 수행한다. 대화 중 첫 종료 요청만으로 미검토 피드백을 자동 승인하지 않아야 한다.
2. A/B 개인 기록에서 마지막 주제의 항목과 챗봇 항목을 조회한다.
3. 완료된 스터디는 ended이고 새 스터디 생성은 새 ID다.
4. 진행 중 스터디가 없는 상태에서 G3는 로컬 앱 프로세스/컨테이너를 재시작하고, G4는 Fargate 앱 태스크를 교체한다. 동일 브라우저로 개인 기록·경험·저장 이미지를 다시 조회한다. 로컬은 PostgreSQL volume/미디어 파일이, AWS는 RDS/S3 데이터가 남아 있어야 한다.

이는 저장 검증이며 진행 중 연결 복구나 중단 세션 이어하기 검증을 추가하는 것이 아니다.

## 4. UI/계약 독립성 검증

S3가 챗봇 폭과 주제/피드백 배치를 수정하고 버튼 하나를 다른 위치로 옮긴다. DTO·HTTP·event·tool 이름 변경 없이 동일 E04~E06을 수행한다. DOM selector나 컴포넌트 ID 변경 때문에 챗봇 기능이 깨지면 계약 경계를 다시 분리한다.

디자인 확인은 로컬 주색/의미색, Pretendard/제한된 Montserrat, Material Symbols, 라이트 모드, 실제 SEED 컴포넌트 사용을 대상으로 한다. 다크 모드와 PRD에 없는 타이머를 새 인수 조건으로 추가하지 않는다.
