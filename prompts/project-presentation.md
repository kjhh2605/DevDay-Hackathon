# 프로젝트 발표 PPT 작업지시서

상태: 초안 — 인터뷰로 다듬는 중

## 목표와 원하는 결과

프로젝트 발표에 사용할 PPT를 준비한다. 서비스의 디자인 시스템과 기존 에셋을 최대한 활용해 서비스와 발표 자료에 통일감을 준다. 아래 발표 흐름을 살리면서 해커톤의 여섯 심사기준에 맞춰 프로젝트의 가치를 전달한다.

## Astra에 맡길 범위

10분 발표에 맞춘 슬라이드별 구성·문구·디자인 지시서를 작성한다. 실제 PPT 파일 제작은 이번 실행 범위에 포함하지 않는다.

프로젝트 코드를 참고해 실제 구현을 반영하여 작성한다. 기능, 모델 활용, 판단 방식과 작동 결과를 지어내지 않는다.

구현된 서비스의 실제 화면을 캡처하고, 설명할 부분을 강조하는 등 발표용으로 다듬은 캡처본을 포함해 서비스 흐름 섹션을 지시서에 작성한다.

## 발표 흐름과 담을 내용

아래 순서는 사용자가 제시한 이야기의 흐름이다. 각 항목이 반드시 한 장의 슬라이드를 뜻하지는 않는다.

1. **관심과 공감으로 시작**
   - “AI가 인간을 대체할까?”라는 질문과 FOMO로 관심을 끈다.
   - “친구의 역할, 새로운 사람과의 만남도 대체할까?”라는 질문으로 공감을 이끈다.
   - AI가 취업 기회를 대체한다는 불안에서 출발해, 기존에는 새로운 사람을 만나 함께하던 스터디 역시 AI로 대체할 수 있게 되는 상황으로 이야기를 확장한다.
   - 도입의 핵심 메시지는 “그럼에도 인간관계는 여전히 중요하다”이다.
   - 이 메시지에서 구체적인 서비스 기능으로 이어지는 연결은 서비스의 실제 사용 맥락에 맞춰 정리한다.
2. **주요 기능 소개**
   - 개인의 경험과 관심사를 저장한다.
   - 스피킹을 진행하며 저장한 경험과 관심사를 자연스러운 대화 주제로 연결한다.
   - AI에 도구를 제공해 채팅으로 대부분의 동작을 처리하는 간편한 UI/UX를 보여준다.
3. **실제 화면으로 보는 서비스 흐름**
   - 구현된 서비스를 실제로 실행해 캡처한 화면을 넣고, 사용자가 서비스를 이용하는 순서에 따라 배치한다.
   - 경험·관심사 저장, 스피킹과 대화 주제 연결, 채팅을 통한 동작 처리 등 주요 기능 중 실제 구현된 흐름을 보여준다.
   - 각 캡처에 사용자의 행동과 화면에 나타난 결과를 설명해 화면 간 연결을 이해할 수 있도록 한다.
   - 캡처는 단순 첨부로 끝내지 않고, 관객이 설명 중인 위치와 핵심 내용을 바로 알아볼 수 있도록 강조 표시와 짧은 설명을 함께 구성한다.
   - 화면과 설명에 맞게 강조 테두리·화살표·부분 확대·주변 영역의 명도 낮추기 등을 선택해 적용한다. 모든 효과를 일괄 적용하기보다 설명할 부분으로 시선을 유도하도록 다듬는다.
   - 강조 표시와 설명의 스타일은 서비스 디자인 시스템과 통일하고, 발표 화면에서도 핵심 UI와 글자가 읽히도록 크기와 배치를 조정한다.
   - 캡처 편집은 설명을 돕는 범위로 한정하며 실제 UI의 내용이나 작동 결과를 바꾸지 않는다.
   - 캡처본을 지시서에 포함하고 해당 슬라이드에서 사용할 이미지 파일 경로를 명시한다.
   - 실제 화면 대신 목업이나 생성 이미지를 구현 화면처럼 제시하지 않는다. 실행 또는 캡처하지 못한 부분은 확인하지 못한 상태로 표시한다.
   - 이 섹션을 포함한 전체 발표 분량을 10분에 맞춘다.
4. **기술 소개**
   - OpenAI의 모델을 어떤 용도로, 어떻게 활용했는지 설명한다.
   - 구체적인 모델명과 기능별 연결 관계는 프로젝트 코드에서 확인해 작성한다.
5. **STT의 한계와 보정 과정**
   - STT 결과를 LLM으로 보정하는 접근을 설명한다.
   - 일반 전사문만 전달하면 사용자가 LLM이 무엇을 보정했는지 알기 어렵다는 문제를 다룬다.
   - 이를 해결하기 위한 보정문 확인 및 사용자 직접 수정 기능을 소개한다.
6. **문장 단위 저장과 챗봇 권한 판단**
   - 사용자가 제시한 “STT가 문장을 판단하지 못하는 문제”와 문장 단위 저장 방식을 설명한다.
   - 사용자는 이때 활용한 기술을 “OpenAI의 decisoins 모델”이라고 지칭했다. 이 표현은 사용자 명칭이며, 정확한 모델명과 API 명칭은 아직 확인하지 않았다.
   - 프로젝트 코드에서 실제 사용한 모델과 호출 방식, 문장 단위 저장 및 챗봇 권한 판단의 동작을 확인해 설명한다. 명칭이나 구조를 추측해서 채우지 않는다.

## 심사기준에 맞춰 강조할 내용

| 심사기준 | 발표에 연결할 내용 | 추가로 필요한 근거 또는 미정 사항 |
|---|---|---|
| 01 문제 정의와 필요성 | 도입의 공감과 서비스가 해결하는 문제를 연결한다. | 누가 어떤 문제를 겪는지, 해결 필요성, 기존 방법의 한계 |
| 02 AI 판단과 해결 방식 | 경험·관심사의 대화 주제 연결, STT 보정, 문장 단위 저장 판단, 챗봇 권한 판단을 설명한다. | 코드에서 확인한 각 판단의 입력 정보·결과·사용 모델과 AI 역할의 적절성 |
| 03 작동하는 결과물 | 구현된 화면의 실제 캡처를 서비스 이용 순서대로 보여주며 주요 기능과 채팅 중심 UI/UX의 흐름을 설명한다. | 실제 구현·작동 범위와 캡처본, 필요한 소프트웨어·데이터·AI·디바이스의 연결 여부 |
| 04 검증과 개선 | STT 한계와 보정문 확인·직접 수정 기능을 문제와 개선의 흐름으로 연결한다. | 직접 확인한 실패 사례, 테스트나 사용자 피드백, 개선 후 확인 결과 |
| 05 사업성 및 도입 가능성 | 매출 가능성뿐 아니라 기업·공공기관·학교·지역사회에서의 도입 가치와 지속 사용 가능성을 다룬다. | 실제 구매·도입 대상, 비용 대비 가치, 계속 사용할 이유, 운영 방법과 검증 상태 |
| 06 Codex 활용 과정 | Codex에 맡긴 작업과 결과를 검토·수정·통합한 과정을 설명한다. | 실제 맡긴 작업, 검토·수정·통합 사례 |

사업성의 이용자·도입 대상은 현재 미정이다. Astra가 실제 서비스를 파악한 뒤 적합한 방향을 제안한다. 위 후보 모두를 채택한 것으로 해석하지 않으며, 검증 자료가 없는 사업성 제안은 가설로 표시한다.

## 근거를 표현하는 원칙

- 직접 확인한 결과, 아직 검증하지 못한 가정, 다음 발전 방향을 구분한다.
- 기능 설명만으로 구현 완료나 사용자 검증 완료를 주장하지 않는다.
- 사용자가 설명한 발표 내용과 코드의 실제 구현이 다르면 그 차이를 명시하고, 구현된 것처럼 꾸미지 않는다. 코드에서 확인할 수 없는 사용자 피드백·사업 검증·Codex 작업 과정도 추측하지 않는다.
- 팀 규모, 장비 가격, 토큰 사용량 자체를 성과로 강조하지 않는다. 필요한 품질을 유지하면서 비용·대기 시간·반복 작업을 줄인 사실이 있다면 그 근거를 설명한다.
- 하루 동안 사업이나 현장 검증을 완성할 필요는 없다는 심사 안내를 반영한다. 없는 수치나 검증 결과를 만들어 넣지 않는다.
- 세부 배점과 제출물 가이드는 추후 안내 예정이며 현재 미정이다.
